# 대용량 데이터·다중 문서 강화 실측

2026-10-30, Linux/Python 3.14.4. 모든 대형 입력은 실행 시 생성한 합성 자료이고 `.harness/intelligence/`에만 보관했다. 원시 세션·실제 업무 자료·큰 CSV·색인 DB를 공개 커밋하지 않았다. 공개 [수치 JSON](../benchmarks/intelligence.json)과 [재현 명령](intelligence.md)을 제공한다.

## 실행 자원과 방법

시작 시 CPU/affinity 16, 호스트 MemAvailable 약 25GB, 디스크 여유 약 695GB를 관찰했다. cgroup memory/cpu 파일은 노출되지 않았고 address-space rlimit는 무제한이었다. **호스트 수치를 컨테이너의 보장된 한도로 해석하지 않았다.** 데이터 엔진은 SQLite 8MiB cache와 디스크 spill을 사용한다. Linux의 별도 Python 프로세스 `ru_maxrss` 피크를 측정했으며 Python 인터프리터도 포함한다. 엄격한 메모리 상한이나 모든 입력 크기의 O(1) 증명은 아니다.

각 크기는 n=1이고 캐시·외부 부하를 통제하지 않았다. 행 생성 시간은 분석 시간에서 제외했다. 중복·결측·NaN을 주입한 2개 사실 파일과 10행의 차원 파일을 JOIN했다. 정답은 별도의 정수 센트 계산·모듈러 규칙으로 산출했다. 전 행 ID set을 정답 생성에 만들지 않았다.

| 파일 분석 | 시간 | 피크 RSS | 유효 / 제외 | 정확한 합계 |
| --- | ---: | ---: | ---: | ---: |
| 100,000행·JOIN | 2.546초 | 26,552KiB | 97,166 / 2,834 | 48,099.75 |
| 1,000,000행·JOIN | 26.357초 | 35,476KiB | 971,669 / 28,331 | 480,979.14 |

100만 행 제외는 결측 9,901, NaN 9,612, 중복 8,818로 대사됐다. 그룹별 합계와 JOIN 무증폭 검사가 통과했다. 임시 SQLite는 약 11.69MB였고 종료 후 제거됐다. 10배 행 수에서 관찰 RSS는 약 1.34배였지만 다른 그룹 수·레코드 폭·정밀도·파서 형식에 그대로 일반화할 수 없다.

독립 Auditor도 별도의 100만 행(조건 다름: JOIN 없음, 1,000그룹 중 5개 출력)을 실제 실행했다. 19.552초, 32,132KiB, 정확 합계 100,000.0과 전체 유효 수를 확인했다. [독립 감사 원문](reviews/intelligence.md)에 조건과 결과가 있다.

## 기존 도구와 같은 입력 비교

같은 100,000행 판매 CSV, 전 행 유효·4그룹·합계 10,000.00을 기존 `clean_sales_csv + aggregate_by_region`과 새 엔진에서 실행했다.

| 경로 | 시간 | 피크 RSS |
| --- | ---: | ---: |
| 기존 문자열 읽기·tuple 유지 | 0.526초 | 87,836KiB |
| 새 스트리밍·SQLite | 1.886초 | 26,460KiB |

이 조건에서 새 경로는 약 3.6배 느리고 RSS는 약 70% 적었다. 작은 입력에는 기존 도구를 유지하고, 큰 입력·여러 파일 JOIN·키 수가 많은 분석에 새 엔진을 선택한다. 서로 다른 JOIN/불량 행 조건의 표를 같은 성능 비교로 섞지 않았다. DuckDB는 설치되지 않아 SQLite만 사용했으며 DuckDB/Parquet 경로를 검증했다고 주장하지 않는다.

## 120문서·근거팩

120개 Markdown 합성 문서, 약 1,233,295바이트, 23,991개 구간에 기본 규정·변경·예외·최신 초안·기록과 비슷한 교란 식별자를 배치했다. 핵심 정보는 첫 부분·중간·마지막에 나눴다. 별도 테스트는 TXT/CSV/JSON/JSONL/PDF/DOCX/XLSX를 실제 합성 파일로 검증했다. **120문서 성능 자료는 혼합 형식이 아닌 Markdown 자료**다.

| 작업 | 측정 |
| --- | ---: |
| 파일 인벤토리 | 0.0053초 |
| 첫 색인 | 3.421초 |
| warm 재구축 | 0.452초 |
| 최종 8MiB cache 별도 색인 프로세스 | 0.708초 / 34,044KiB |
| 경계 식별자 검색 5개 | 0.520초 합계 |
| 식별자 Evidence Pack | 0.518초 / 7,066자 |
| 원문 해시·위치·발췌 검증 | 0.0059초 |
| 결정적 FACT 종합 | 0.0057초 |

첫 구축과 warm 재구축의 차이를 알고리즘 개선 효과로 주장하지 않는다. 정확 식별자는 쿼리별 제한된 별도 프로세스를 사용하므로 빠른 부분 문자열 검색(초기 5개 합계 0.031초)보다 느릴 수 있다.

부분 문자열은 BASE-42가 BASE-420에도 맞아 선택 팩의 관련 근거 정밀도가 **5/7 = 71.4%**였다. 경계 식별자 모드에서 **5/5 = 100%**, 핵심 근거 보존율 **5/5 = 100%**, 인용 검증률 **100%**를 확인했다. 이는 정해진 5개 식별자와 합성 교란 자료의 점수이며 일반 의미 검색의 정밀도·재현율이 아니다. 팩은 원문 바이트 수 대비 약 0.57% 크기였고 10,000자 제한을 지켰다. 이 사례는 ASCII 중심 근거라 문자/바이트 수가 같았으며 한국어 자료에서는 다를 수 있다.

시행 기본 한도 110kg, 긴급 승인 시 120kg, 최신 미시행 초안 999kg 제외를 검증했다. 별도 동시 시행 상충 사실은 Conflict, 정보가 없는 요청은 Missing Evidence/answer null로 판정했다. 문서 주장과 다중 파일 합계는 CLI `evidence compare`로 재계산해 0.30kg 일치·0.31kg 불일치·보고서 변조를 검증했다.

## 실제 Codex 제한 컨텍스트 시범

별도 새 문맥의 Synthesizer는 전체 1.23MB 원문이나 정답 파일을 읽지 않고 **9,479자짜리 초기 literal 팩만** 읽었다. 110kg 기본·120kg 조건부 예외·115kg 기록·초안 배제·조건 미확인을 정확히 보고했다. 독립 Auditor가 실제 원본의 정확한 줄과 헤더를 재확인해 답변 항목 5개·출처 인용 5개, 팩 인용 전체 7개를 검증했다. 115kg 기록만으로 긴급 승인 조건이 충족됐다고 추정하지 않았다.

7,066자 개선 팩과 시범에 사용한 9,479자 팩은 구분해 보관했다. 모델 시범의 입력을 사후에 더 작은 팩으로 바꿨다고 보고하지 않는다. 실제 모델은 Sol 6.1의 역할 프롬프트이며, 이 실행 세션에 새 synthesizer selector가 없어서 제공 도구의 새 컨텍스트 fallback을 사용했다. task-only 모델 토큰을 분리 계측하지 않았다. 결정적 벤치마크 자체의 모델 호출은 0회이며 전체 개발·시범의 AI 사용량이 0이라는 뜻은 아니다.

새 Skill 3개와 synthesizer 이름은 `codex debug prompt-input`의 실제 로컬 프롬프트에서 발견됐고, 전체 Skill 20개가 구조·참조 검사를 통과했다. debug 원문은 공개하지 않았다. 자동 선택은 모델과 제공 플랫폼에 달려 있으며 CLI 도구 자동 호출을 모든 환경에서 보장하지 않는다.

## 독립 리뷰·현재 검증

감사자가 5개 결함(FACT 소수 손실, JSON 소수 손실, 같은 구간의 먼 검색어 누락, 무제한 JSONL 레코드 읽기, 부분 추출 자료의 잘못된 supported)을 재현했다. 수정 후 감사자가 각각 재실행했다. 후속 계산 비교 감사에서는 보고서 단위 라벨 변조 결함도 찾아 수정·재검증했다. root 통합 과정에서 stdin 기반 regex 프로세스 실행 실패도 재현해 별도 subprocess 방식으로 수정했고 회귀 검사가 통과했다.

`make check`: 기존 포함 **단위 62개 + solution 3개 + 기존 A/B/C 3개**가 통과했고, 설정·계획 검사도 통과했다. 새 예제의 실제 CLI profile/inventory/index/search/evidence-pack/verify/synthesize/compare를 실행했다. 큰 입력은 Git 제외이고 별도 benchmark 명령으로 재생성한다. 기존 작은 판매 데이터 인터페이스와 이전 벤치마크 출력은 보존했다.

## 적용 범위와 미검증

- 자유 문장의 자동 의미 이해 엔진은 아니다. 결정적 종합은 명시적 FACT 원문 행을 처리하며, 일반 문서는 제공 Codex의 근거 기반 해석과 독립 감사가 필요하다.
- 문서 진위·외부 승인·불완전한 manifest는 해시/인용 검증만으로 인증되지 않는다. 예외 조건의 실제 충족을 별도 확인해야 한다.
- PDF OCR·표 레이아웃 복원, DOCX의 모든 부속 텍스트, XLSX 수식 재계산·날짜 서식은 지원하지 않는다. 알려진 미추출 부분은 partial/unsupported/error로 반환한다.
- 검색은 구간 경계를 넘지 않는다. 정확 식별자 경계·메타데이터 스키마도 도메인에 맞게 확인해야 한다. FTS5는 형태소·의미 검색이 아니다.
- 무제한 JSON 배열·초대형 단일 레코드는 의도적으로 처리하지 않는다. JSONL 분할·검증된 명시적 인코딩 등 대체 경로가 필요하다.
- 증분 색인·벡터 DB·DuckDB 고급 경로는 구현하지 않았다. Python 3.11+ 문법을 사용하지만 실행 검증 버전은 3.14.4다.
- 집계·출처 확인은 단일 결정적 CLI가 적합하다. 여러 독립 조사와 원본 감사는 역할 분리가 유용했지만 이번 작업에서 에이전트 팀의 속도 우위를 측정하지 않았다.
- 시험 당일 제공 버전·모델·파서·정책 접근성은 재확인해야 한다. 기존 시험 제한과 AI 금지 필기 단계 원칙을 유지한다.
