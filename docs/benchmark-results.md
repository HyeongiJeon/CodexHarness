# 실제 실행·검증 보고서

준비 환경: Python 3.14.4, `codex-cli 0.163.0`, Linux. 실행 시각은 2026-10-30 KST이며 공개 근거의 타임스탬프는 UTC다. Codex 업데이트·인증 복제·권한/관리 설정 변경·브라우저 자동화는 수행하지 않았다. 웹·판매 데이터·티켓 과제는 합성 입력이다.

## 측정 결과

동일한 A/B/C 명세로 단일과 멀티를 각각 한 번 정상 실행했다. 최종 평가기로 두 결과를 다시 검사했다. wall time은 CLI 프로세스 시작부터 종료까지이며 후속 로컬 검사는 제외한다.

| 구성 | CLI 시간 | 실제 자식 | CLI 종료 | 최종 수용 검사 | 관찰 토큰 합계 |
| --- | ---: | ---: | ---: | --- | ---: |
| 단일 Sol 6.1 / high | 91.709초 | 0 | 0 | A/B/C 3/3 통과 | 221,725 |
| 역할별 멀티 | 207.223초 | 4 | 0 | A/B/C 3/3 통과 | 1,344,725 |
| 모델 상속 smoke | 23.101초 | 2 | 0 | 두 JSON 출력·새 문맥·병렬 확인 | 252,741 |

**이 작은 과제에서는 멀티가 단일보다 2.26배 오래 걸렸고 관찰 토큰도 약 6.06배였다. 속도 향상은 관찰되지 않았다.** 모델 초기화, 컨텍스트·도구 설명, 위임·검토 비용이 있다. 멀티 실행에서는 데이터 경계 결함을 발견해 수정하는 추가 작업도 수행했다. 작은 수정에는 리드가 직접 작업하고, 충분히 독립적이며 큰 작업에만 병렬 팀을 활성화한다. 180분 실제 과제에서의 속도 개선은 측정하지 않았다.

토큰은 부모 `turn.completed`의 input+output과 실제 자식 세션의 `total_token_usage` 합계다. 멀티는 부모 686,786 + 자식 657,939다. **캐시 토큰을 포함**하며 reasoning 토큰을 output에 다시 더하지 않았다. 과금 금액·동일 비용·정확한 서버 비용을 뜻하지 않는다. n=1이고 모델·캐시·실행 시각·시스템 부하를 통제하지 않아 통계적 성능 결론을 내릴 수 없다.

## 실제 위임과 문맥 증거

최종 멀티의 실제 역할·모델·강도:

| 역할 | 모델 | 강도 | 실제 출력 |
| --- | --- | --- | --- |
| main | `gpt-6.1-sol` | high | 통합 검사·수정 지시·최종 실행 |
| frontend | `gpt-6.1-sol` | medium | `web/server.py` |
| data | `gpt-5.6-terra` | high | `analysis/report.py` |
| core | `gpt-6.1-sol` | high | `repair/tickets.py` |
| qa | `gpt-5.6-terra` | high | CSV 경계 재현·독립 확인 |

세 구현 자식은 각각 21:43:20, 21:43:23, 21:43:26 UTC에 시작했다. core는 21:43:51, frontend는 21:44:01에 종료해 실행 구간이 겹친다. QA는 추가 결함이 발견됐을 때 활성화했다. 실제 생성 요청의 `fork_turns="none"`, 자식 세션의 부모 관계·역할·모델·강도·종료 시간을 대조했다. `forked_from_id`는 null이다. 단순 완료 메시지의 “병렬 실행했다”는 문장은 증거로 사용하지 않았다.

상속 smoke의 requirements와 explorer는 둘 다 부모의 `gpt-6.1-sol / high`로 실행됐고 실제 실행 구간도 겹쳤다. 부모에게만 준 마커는 자식 로그와 출력에 없었다. 앞선 routed smoke에서는 requirements가 Sol 6.1/high, explorer가 Luna 6/medium으로 실행됐다. 이 routed smoke는 사용자 중단으로 바깥 수집기가 종료됐으나 CLI의 `turn.completed`, 두 출력 파일·검사와 자식 세션 증거를 별도로 회수했다. 성공한 상속 smoke와 혼동하지 않는다. 이는 제한된 문맥 분리 검사이며 파일 격리나 보안 경계를 증명하지 않는다.

`.agents/skills`의 17개 항목은 제공 세션의 실제 자동 발견 목록에 표시됐다. smoke에서 requirements가 `requirement-discovery/SKILL.md`를 읽었다. 모든 Skill을 실전 과제로 실행했다는 뜻은 아니다. 17개 구조·메타데이터·참조 링크 검증은 별도로 통과했다.

## 검증 시나리오와 실제 결함

| 시나리오 | 검사 | 결과·범위 |
| --- | --- | --- |
| A 업무 웹앱 | 실제 loopback HTTP 목록·추가·상태 변경·400/404·HTML/JS 계약 | 통과. 브라우저 렌더링·키보드·좁은 화면 수동 검증은 미확인 |
| B 데이터 분석 | CSV 결측·중복·무효 값 제외, 최초 유효 ID, Decimal 기반 정확한 집계 | 통과. 기본 예제 정제 5행, 제외 사유 4개; North 46.00, South 10.00 |
| C 기존 결함 수정 | 마지막 티켓 누락 starter의 실제 실패 → 별도 solution 회귀 | starter exit 1 예상대로 재현; solution 3개 검사 통과 |
| 하네스 전체 | 단위 27 + solution 3 + 보존된 native 결과의 A/B/C 3 | 총 33개 동작 검사, 설정·Skill·계획 검사 통과 |

독립 초기 리뷰는 **하네스 결함 8개와 의도적 fixture 결함 1개**를 재현했다. 모델 상속 번들·메인 라우팅 누락, 경로 정규화 우회, 날짜·금액 예외, PATCH 예외 이후 진행, 큰 합계 정밀도, 잘못된 계획 구조를 수정했다. 독립 최종 감사가 테스트 출력 집계 결함 1개를 추가로 발견했다. 위치·재현·검증 범위는 [초기 리뷰](reviews/initial.md), [최종 감사](reviews/final.md)에 기록했다.

최종 네이티브 멀티에서도 큰 유효 금액의 `InvalidOperation`과 잘못 인용된 CSV 행 뒤의 유효 행 누락을 리드가 재현했고, data 담당자가 수정한 뒤 QA·리드가 확인했다. 코드 변경 및 최종 출력은 보존했다. 정확한 수정 재시도 횟수는 계측하지 않아 null로 남긴다. data에 보낸 조정 메시지를 모두 수정 횟수로 계산하지 않는다. 파일 충돌 역시 전수 자동 계측하지 않았다. 쓰기 범위를 분리했고 관찰한 통합 결과에서 충돌은 드러나지 않았지만 잠금이나 격리를 보장하지 않는다.

## 실패·보고 오류도 보존

- 첫 멀티 pilot은 197.476초 후 계정 사용량 한도로 CLI exit 1이었다. 내부 통합 검사 19개는 통과했지만 전체 실행 성공으로 처리하지 않았고 속도 비교에서 제외했다.
- 이어진 상속 smoke도 한도로 2.518초 후 실패했다. 모델·계정·인증을 바꾸지 않았다. 사용량 초기화 안내 시각이 지난 뒤 정상 상속 smoke와 단일·멀티를 다시 실행했다.
- 초기 외부 평가기는 명세에 없던 “빈 결과에도 unknown=0 키를 반드시 포함”을 요구했다. 이 과도한 기대를 제거하고 기존 출력에서 다시 실행해 통과를 확인했다. 원본 실패 로그는 유지했다.
- 두 번째 멀티 프로세스는 실행 중 변경 전 평가기를 이미 로드했다. HTTP 요청 로그가 unittest 줄 사이에 끼어 원본 요약의 `scenarios.A=false` 표시가 잘못됐다. CLI·전체 acceptance exit은 0이었다. 최종 평가기는 구조화된 per-scenario JSON을 수집하며, 같은 파일의 최종 재검사에서 A/B/C 모두 true다. 원본 요약을 덮어쓰지 않았다.
- 단일·상속 smoke는 최종 `orchestration_verified` 필드 추가 전 실행됐다. 공개 근거는 필드를 실행 당시 있었던 것처럼 만들지 않고, 최종 판정식의 사후 재계산임을 구분한다.

## 재현과 공개 근거

```sh
make check
python3 -m harness benchmark-check benchmarks/sample
python3 -m harness data examples/data/sales.csv
python3 -m harness benchmark --mode smoke --routing inherited --timeout 180
```

앞의 세 명령은 AI·네트워크가 필요 없다. 마지막은 제공 Codex를 실제 실행해 사용량을 소비한다. 공개 [측정 사실 JSON](../benchmarks/evidence.json), [실제 멀티 출력](../benchmarks/sample/TASK.md)과 SHA-256으로 보존된 파일을 확인할 수 있다. 세션 전문·도구 payload·인증정보는 공개하지 않았다. 실제 원시 증거는 준비 머신의 Git 제외 `.harness/runs/`에 남는다.

최종 로컬 `make check`는 통과했다. 준비용 공개 저장소 `HyeongiJeon/CodexHarness`의 main에 `7c52ec0f07208a798007f70fddaabf36c648a0af`까지 push한 뒤, credential helper와 HTTP 추가 인증 헤더를 비운 HTTPS clone을 새 임시 디렉터리에 수행했다. clone exit 0, 같은 커밋 확인, **새 clone의 `make check` exit 0**, Git 작업 트리 clean을 확인했다. 원시 `.harness/`는 clone에 존재하지 않았다. 이후 변경은 이 게시·재현 사실을 기록하는 문서뿐이다. 최종 문서 커밋도 같은 공개 main에 게시한다. PR 정책이 없는 빈 공개 저장소에서 시작해 단계별 커밋을 유지했고 PR·별도 병합은 만들지 않았다. 시험 환경에서는 push하지 않는다.

## 남은 확인 사항

현재 미확인은 **실제 브라우저 수동 화면 검증**과 **당일 시험 설치 버전·모델·네이티브 도구 접근성**이다. 화면 확인 요청은 전달했으며 답변 없이 통과 처리하지 않았다. Python 3.11 호환 문법을 사용하지만 실제 실행 검증 버전은 3.14.4다. 최신 공개 소스 전체나 다른 CLI 버전, 모든 Skill의 도메인 작업, 모든 입력 범위를 테스트하지 않았다. 공식 버전 차이와 사용 불가 시 대안은 [조사](codex-research.md)·[시험 안내](exam-runbook.md)에 있다.
