# 리드의 단계별 운영 절차

이 저장소는 개발 보조 도구다. 실제 과제의 요구사항, 기존 코드·테스트·`AGENTS.md`가 우선한다. 다른 프로젝트에 전체 저장소를 복사하거나 기존 설정을 덮어쓰지 않는다. 필요한 역할 프롬프트와 스킬만 해당 프로젝트 지침에 맞게 적용한다. 실행 준비는 [시험 실행 안내](exam-runbook.md), 설정 근거와 버전 차이는 [Codex 조사 기록](codex-research.md)을 따른다.

리드의 주 문맥에는 수용 기준, 중요한 결정, 의존성·담당자·상태, 통합 검증 증거만 남긴다. 긴 탐색 결과나 작업 로그를 계속 붙이지 않고 경로와 짧은 결론을 받는다. 스킬은 필요한 작업이 생길 때 해당 `SKILL.md`를 읽는다. 스킬은 절차이며 별도 에이전트가 아니다.

## A. 요구사항과 저장소 탐색

`requirements`와 `explorer`를 각각 새 문맥으로 시작하고, 둘을 시작한 뒤 결과를 기다린다. 요구사항 담당자는 필수·선택 범위, 수용 기준 ID, 경계 사례, 이해관계자 질문을 반환한다. 탐색 담당자는 관련 파일, 구조, 의존성, 실행·검증 명령, 기준선 오류를 읽기 전용으로 조사한다. 질문은 리드가 모으고, 과제에서 허용한 경우에만 이해관계자에게 전달한다.

각 위임에는 다음 내용을 명시한다. 처음부터 모든 저장소 내용을 전달할 필요는 없다.

```text
역할: requirements / explorer 중 하나
목표: 이번 요청에서 필요한 최소 조사
입력: 과제 원문 경로, 기존 README와 AGENTS.md, 관련 경로
허용 쓰기 경로: 없음 (필요 시 지정된 개별 증거 파일만)
제약: 다른 작업자도 같은 파일 시스템을 사용함. 타인의 변경을 되돌리지 말 것.
반환: 수용 기준 또는 파일 지도, 관찰 근거, 미확인 사항, 리드에게 보낼 질문
```

새 문맥은 대화 분리이며 파일 격리가 아니다. 현재 제공된 도구 스키마를 읽고 사용한다. hosted 도구의 `fork_turns: "none"`와 설치 CLI V1의 `fork_context: false`는 서로 다른 API다. V1에서 `fork_context: true`는 전체 대화를 복제하며 역할 선택과 함께 사용할 수 없다. V2 활성 여부도 별도로 확인한다.

## B. 아키텍처와 작업 계약

`architect`는 A의 간결한 결과와 기존 구조를 받아 가장 작은 완전한 핵심 흐름을 설계한다. 작업마다 `id`, `role`, `objective`, `inputs`, `outputs`, `acceptance`, `paths`, `depends_on`, `verify`를 반환한다. 인터페이스·데이터 형식·오류 처리를 먼저 합의하고, 담당 경로와 검증 명령을 실제 프로젝트 구조에 맞춘다.

[작업 계획 예제](../examples/task-plan.json)는 합성 연습용 계약이다. 다음 명령은 의존성 순환, 누락 필드, 동시에 실행 가능한 작업의 경로 충돌을 검사한다. 작업을 실행하거나 기능의 정확성을 증명하지는 않는다.

```sh
python3 -m harness plan-check examples/task-plan.json
```

선행 작업이 같아도 두 후속 작업은 병렬로 실행될 수 있다. 한 작업의 경로가 다른 작업의 상위 디렉터리인 경우에도 충돌한다. 경로를 넘길 때는 선행 작업 완료와 소유권 인계를 명시한다. 검사기가 허용하는 순차 중복도 자동 잠금은 아니다.

## C. 필요한 구현 담당자만 활성화

유효한 동시 한도를 먼저 확인한다. 이 저장소의 운영 기준은 리드와 작업자 3명이며, 더 작은 호스트 한도나 관리 제한이 우선한다. 3–4명의 작업자가 가능하면 유용한 독립 작업에 배정하되 숫자를 채우려고 일을 나누지 않는다. 설정 숫자만 보고 실제 병렬 실행을 주장하지 않는다. V1·V2는 동시 한도에서 리드를 세는 방식도 다를 수 있다.

| 담당 | 적합한 책임 | 소유권 예시 |
| --- | --- | --- |
| core | 업무 로직, API, 복잡한 수정 | `src/service/` |
| frontend | 핵심 화면 흐름, 입력·빈 상태·오류 표시 | `src/ui/` |
| data | 스키마, 정제, 계산 검증 | `src/analysis/` |
| docs | 실제 동작과 실행 증거의 문서화 | 지정된 문서 파일 |

모든 작성자에게 다른 작업자와 파일 시스템을 공유하며 타인의 변경을 되돌리지 말라고 알린다. 같은 파일을 여러 담당자에게 주지 않는다. 공통 manifest·lockfile·환경 설정·통합 파일은 리드가 소유하며, 필요하면 한 명에게 명시적으로 넘긴다. 중간 결과는 변경 경로, 수행 명령·종료 코드, 남은 문제로 받는다. 완료한 에이전트의 슬롯은 도구가 지원하는 종료 방식으로 정리하고 다음 역할에 사용한다. 중첩 위임은 기본적으로 사용하지 않는다.

기본 라우팅의 `data`·`qa` 선호 모델은 정확히 `gpt-5.6-terra`다. `gpt-6.1-terra`와 다른 모델이며 별칭으로 취급하지 않는다. 모델·역할 선택이 노출되지 않거나 접근이 실패하면 검증된 부모 모델을 상속하는 새 에이전트에 역할 프롬프트를 보낸다. 새 에이전트도 사용할 수 없으면 같은 리드가 역할별로 순차 수행하고 독립 검토가 빠졌음을 기록한다. 우회를 위해 권한·인증·신뢰 설정을 바꾸지 않는다.

## D. QA와 독립 리뷰

구현 담당자의 자체 점검 뒤, 새 문맥의 `qa`는 통합 대상의 수용 기준을 실행하고 실패를 재현한다. 별도의 새 문맥 `reviewer`는 실제 코드·diff·요구사항을 읽고 정확성·회귀 결함을 검토한다. 작성자의 설명만으로 통과시키지 않는다. 두 역할은 읽기 전용을 기본으로 하며 구현 수정은 소유권을 넘겨받은 뒤에만 한다.

발견 사항은 심각도, 사용자 영향, 파일·위치, 재현 명령·입력, 기대·실제 결과, 최소 수정 방향을 포함한다. 결과가 없으면 확인 범위와 불확실성을 보고한다. 치명적·핵심 기능 결함부터 고치고 같은 재현과 관련 회귀 검사를 다시 실행한다. 스타일만 바꾸는 왕복은 피한다. 브라우저 자동화·GUI·computer-use는 사용하지 않는다.

## E. 리드의 통합 검증

리드는 실제 diff를 읽고 소유권 충돌과 인터페이스 연결을 확인한 뒤 최종 파일 상태에서 통합 명령을 직접 실행한다. 이 저장소는 `make check`가 기본 검사이며, 다른 프로젝트에서는 원래의 빌드·테스트·실행 명령을 따른다. 작업자의 통과 보고는 리드 실행을 대신하지 않는다.

[증거 템플릿](../templates/evidence.md)에 수용 기준 ID, 정확한 명령, 작업 디렉터리, 종료 코드, 기대·관찰 결과, 증거 경로, 검사한 코드 상태를 기록한다. 해당 코드가 바뀌면 관련 증거를 갱신한다. HTTP 응답 확인은 API 동작 근거이며 화면 렌더링·레이아웃·키보드 동작의 증거가 아니다. 사용자가 수동으로 확인하기 전 시각 검사는 `미확인`으로 남긴다.

## F. 전달

산출물 존재·내용·실행 경로·요구 형식·필수 의존성·알려진 한계·Git 상태를 확인한다. 최종 전달에는 실제 산출물 경로, 실행 명령, 수행한 검사와 결과, 미확인 기준을 적는다. 과제에서 요청한 로컬 제출 방식만 사용한다. 시험 중 Git push와 외부 업로드는 하지 않는다.

[결정 템플릿](../templates/decision.md)과 증거 기록은 사실에 근거한 개발 노트다. 이후 AI 금지 필기 평가에서는 AI 사용을 중단하며 이 도구로 답안·예상 답안을 작성하지 않는다.
